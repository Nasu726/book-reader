# 設計判断の記録

コードには How と What は書かれるが、Why は残らない。「なぜこうなっていないのか」「なぜこの遠回りをしているのか」を、後から読む人（次のエージェントを含む）が再発明しないために記録する。

各項目は **判断 / 理由 / 測った値 / これを覆す条件** で構成する。
時系列の作業記録は `docs/WORKMAP.md` の Execution Log を参照。

## D-1. 認証を Cloudflare Access に委譲する

**判断**
本番デプロイでは Cloudflare Access が認証を行い、アプリは `Cf-Access-Jwt-Assertion` の署名を検証するだけにする。パスワード認証（scrypt）はローカル開発と自己ホスト用に残す。

**理由**
Cloudflare Workers 無料枠の CPU 上限は **10ms/リクエスト**。scrypt は「総当たりを防ぐために計算を重くする」ことが目的の関数なので、この予算に収まらない。パラメータを下げれば収まるが、それは関数の存在理由を捨てることになる。

**測った値**（このマシン、Node 24）

| 経路 | CPU 時間 |
|---|---|
| scrypt 検証 | 51.4 / 64.8 / 67.4 / 74.1 / 78.9 ms |
| Access JWT 検証（鍵キャッシュ後） | 中央値 **1.25 ms**（0.77〜5.89） |

40〜60倍の差。Access なら 10ms 予算の 1/8 で済む。

**副次的な効果**
ログインページ、セッションテーブル、レート制限、パスワードハッシュの管理がすべて不要になる。ただしローカル開発では使えないため、両方の経路を `src/server/auth/current-session.ts` に集約し、`CF_ACCESS_TEAM_DOMAIN` と `CF_ACCESS_AUD` の有無で切り替える。

**なぜ Supabase ではないのか**
無料枠は十分だが、(1) 別プロジェクトと別DBが増える、(2) 無料プランは約7日の無操作でプロジェクトが一時停止し手動復帰が要る、(3) ログイン画面を自前で実装する必要がある。Access は既存の Cloudflare アカウント内で完結し、ログイン画面も IdP 連携も提供される。Zero Trust 無料枠は50ユーザー。

**これを覆す条件**
- Cloudflare 以外へ移行する場合。その時は `current-session.ts` に別の adapter を足す
- 複数人で使い、Cloudflare に載せたくない ID 基盤を使う必要が出た場合

**注意**
ヘッダの存在だけを信用してはいけない。Access を経由せず origin に到達した経路は同じヘッダを自由に付けられる。署名・`iss`・`aud`・`exp` を必ず検証する。`tests/unit/cloudflare-access.test.mts` が偽造・期限切れ・別テナント・`alg: none` 降格を含めて固定している。

## D-2. EPUB のパースをブラウザで行う

**判断**
EPUB の解析はブラウザで行う。サーバは書籍ファイルを開かない。

**理由**
2つの無料枠制約に同時に当たる。

- **CPU 10ms**: 書籍1冊分の zip 展開・XHTML パース・サニタイズがこの予算に収まらない
- **バンドル 3 MiB (gzip後)**: epub-ts + jszip + サーバDOM(linkedom) を Worker に載せると圧迫する

加えて、これは制約への妥協ではなく元々そちらが正しい。EPUB は reflowable であり、再流し込みはブラウザの仕事。ブラウザは表示のために同じ DOM をどのみち構築する。

**構造**
`EpubParser` は epub-ts の `Book` 実装をコンストラクタ引数で受け取る。ブラウザは `@likecoin/epub-ts`、テストは `@likecoin/epub-ts/node` を渡す。同じロジックが両方で動く。

**代償**
書籍のメタデータタイトルを import 時に読めなくなった。代わりに、ブラウザが初回オープン時に本のタイトルを読み、**保存済みタイトルがファイル名そのままの場合に限り** PATCH で差し替える。手動で改名したタイトルは上書きしない。

**これを覆す条件**
Workers Paid（CPU 30秒）へ移行し、かつサーバ側にパース結果をキャッシュしたい要求が出た場合。その時も `document_sections` テーブルは既にある。

## D-3. 文書のバイト列を DB の外に置く

**判断**
`DocumentStorage` 境界を設け、DB には不透明な参照文字列だけを持たせる。ローカルはファイルシステム、本番は R2。

**理由**
当初は base64 data URL として SQLite に格納していた。100MB の上限に対し base64 は約1.33倍に膨れ、開くたびに全体が JSON としてメモリを通り、ブラウザへも JSON で送られていた。論文PDFですら実用にならない。

**なぜ境界を先に作ったか**
デプロイ先が未定の時点で「後で差し替えられる形」だけ確保するため。実際に Cloudflare が選ばれた今、R2 adapter を足すだけで済む。

**互換性**
`data:` で始まる参照は今もその場でデコードして読める。この分離より前に取り込んだ文書が壊れない。

**これを覆す条件**
なし。DB にバイナリを戻す理由は考えにくい。

## D-4. PDF のキャンバスとテキストレイヤーは単一の表示スケールを共有する

**判断**
`cssScale = 表示幅 / ページ幅 × zoom` を1つ計算し、キャンバスとテキストレイヤーの両方に使う。

**理由**
以前はキャンバスを `devicePixelRatio` 倍で描いて CSS で `width:100%` に伸ばし、テキストレイヤーは `scale:1` 前提で配置していた。表示スケールが2系統あるため、選択可能なテキストが実際の文字からずれる。本文が二重に見え、文を選んでも別の語が選ばれる。

**もう一段の原因**
pdf.js のテキストレイヤーCSSを読み込んでいなかった。pdf.js は各テキスト片を絶対配置し CSS カスタムプロパティでサイズを決めるため、スタイルが無いと通常のインラインテキストとして左上から流れる。`globals.css` に必要な規則だけを pdfjs-dist 6.2.108 から取り込んでいる（ビューア全体の 160KB は使わないツールバーとエディタのため）。

**検証**
`tests/e2e/pdf.spec.ts` がキャンバスとレイヤーの矩形一致、テキスト片が絶対配置であること、ページ左余白ぶんオフセットしていること、フォントサイズがスケールに追従していることを固定する。どちらの原因を戻してもテストが赤くなることを確認済み。

## D-5. EPUB 本文は許可リストでサニタイズしてから構造ごと描画する

**判断**
章の XHTML を許可リスト方式（デフォルト拒否）でサニタイズし、見出し・段落・強調を保ったまま描画する。

**理由**
以前は `documentElement.textContent` で全タグを剥がしていた。EPUB の最大の強みは構造を持っていることなのに、読み込んだ直後に捨てていた。結果として `<head><title>` の中身が本文に混入し、段落境界が消えて文が連結していた。

**なぜ許可リストか**
章の XHTML は第三者が書いたもので信用できない。許可リストなら、知らないタグも将来の属性も自動的に落ちる。属性は一つも通さないため `on*` ハンドラ、インラインスタイル、外部参照がまとめて消える。

**なぜ DOMPurify を足さないか**
サニタイズ対象は epub-ts が既に構築した DOM ノードであり、既存の依存だけで完結する。許可リストは約80行で、`tests/unit/html-sanitizer.test.mts` と E2E の `EPUB chapters cannot execute authored scripts` が固定している。

**ブラウザへ移した影響（D-2）**
サニタイズもブラウザで走るようになった。出力の挿入先は同じページなので信頼境界は変わらない。E2E の script 実行テストはブラウザ側で走っており、そのまま守りとして機能する。

## D-6. セッションは端末ごとに持つ

**判断**
`auth_sessions` は1ユーザー複数行。ログアウトは提示されたトークンだけを失効させる。

**理由**
当初のスキーマは `user_id` に UNIQUE を付け、ログイン時に既存行を削除していた。スマホでログインするとPCが黙って切れる。ログアウトは全端末を破棄していた。個人用リーダーは「スマホで読み、PCで続きを読む」使い方が中心なので、この挙動は目的に反する。

**移行**
セッションは使い捨てなので、旧スキーマを検出したらテーブルごと作り直す。全員が一度だけ再ログインする。

**残す機能**
`logoutEverywhere` は資格情報の漏洩が疑われる場合のために残してある。UI からは呼ばない。

## D-7. リーダーの文字サイズは本文だけを拡縮する

**判断**
`--reader-font-scale` を本文に適用する。ルート要素の `font-size` は触らない。

**理由**
以前はルートの `font-size` を変えていたため、アプリ内の全ての `rem` が連動した。80% ではボタンが 44px から 35px に縮み、モバイルのタップ領域が壊れる。180% ではレイアウトが破綻する。「本文を読みやすくする」操作が UI 全体を壊すのは目的に反する。

**同時に見つかった不具合**
`Number(null)` は `NaN` ではなく `0` を返す。未設定時に下限へクランプされ、既定値が 100% ではなく 80% になっていた。

**検証**
`tests/e2e/auth.spec.ts` が、本文が拡大し、かつ操作ボタンの高さが変わらず 40px 以上であることを同時に確認する。

## D-8. ダークテーマはクラスに束ねる

**判断**
`@custom-variant dark (&:where(.dark, .dark *))` を宣言し、`applyThemeToDocument` が `dark` / `light` クラスを明示的に付け外しする。

**理由**
Tailwind v4 は既定で `dark:` を `prefers-color-scheme` に紐づける。テーマトグルが付けるクラスに反応するスタイルが存在せず、ダークテーマは一度も視覚的に効いていなかった。クラスは付いていたので、クラスの有無だけを見るテストでは検出できない。

**`light` クラスも明示する理由**
OSがダークの人が「ライトを選ぶ」を表現できるようにするため。`dark` の有無だけでは「未選択」と「ライトを選んだ」が区別できない。

**検証**
E2E はリーダーペインの計算済み背景色が実際に変わることを見る。`@custom-variant` を消すと赤くなることを確認済み。

## D-9. 検証は条件付きアサーションを禁じる

**判断**
E2E に `if (await locator.isVisible())` を書かない。

**理由**
引き継ぎ時、lint / typecheck / unit 71 / E2E 20 / build がすべて緑の状態で、PDF本文の二重表示、ライブラリのデモPDF残留、EPUB段落消失といった致命的欠陥が同時に存在していた。原因は `pdf.spec.ts` と `ai-answer.spec.ts` の全アサーションが `if (isVisible())` の内側にあったこと。対象要素が消えるとテストは何も検証せず緑になる。`auth.spec.ts` に至っては `/login` に対して実行しており、テーマもフォントもライブラリも全チェックがスキップされていた（D-7、D-8 の不具合が長期間残った理由）。

**運用**
新しいテストを足したら **mutation で確認する**。該当コードをわざと壊し、テストが赤くなることを目視する。赤くならないテストは何も守っていない。

## D-10. 文書所有権の確認を1箇所に集約する

**判断**
`requireOwnedDocument` を `src/server/documents/ownership.ts` に置き、文書に紐づく書き込みを行う全ルートがそれを通る。

**理由**
同じチェックが3ファイルに別名（`documentForUser` ×2、`requireOwnedDocument`）でコピーされ、highlight の POST だけが漏れていた。しかも progress ルートの `requireOwnedDocument` は同名で意味が逆（所有時に `null` を返す）だった。個別にパッチを当てても同じことが再発する構造だったため、実装を1つにした。

**現時点の影響度**
単一ユーザー構成では他人の文書が存在せず、外部キー違反で 500 になるだけ。ただしスキーマもリポジトリも全て `user_id` スコープ設計であり、2人目が増えた瞬間に他人の文書へ書き込める。Access 導入で userId がメールアドレスになるため、複数ユーザーは現実的な話になった。

## D-11. Cloudflare のバインディングは実行環境で判定して掴む

**判断**
D1 と R2 は `navigator.userAgent === "Cloudflare-Workers"` を確認してから `getCloudflareContext()` で解決する。そうでなければローカルの SQLite ファイルとファイルシステムを使う。

**理由**
最初は「バインディングが取れたら Cloudflare」という判定にしていた。ところが `getCloudflareContext()` は `next dev` でも解決してしまい、ローカルのリーダーが**空のローカルD1**を掴んだ。症状は全ページの `D1_ERROR: no such table: documents`。E2Eが用意したSQLiteファイルは一切使われていなかった。

`initOpenNextCloudflareForDev()` を外しても解決したので、これは開発用フックの有無ではなくコンテキスト解決そのものの挙動である。実行環境を直接聞くのが正しい。

**同じ理由で `next dev` にバインディングを渡さない**
`initOpenNextCloudflareForDev()` は `USE_CLOUDFLARE_BINDINGS=1` のときだけ有効にする。ローカル開発とE2Eは SQLite とファイルシステムを前提に組み立てられており、そこへD1とR2を差し込むと全部壊れる。Cloudflare経路の検証は `npm run cf:preview`（実Workerランタイム + 実バインディング）で行う。

**これを覆す条件**
E2E自体をCloudflare経路に対して走らせたくなった場合。その時は `cf:preview` に対する別プロジェクトを足す。

## D-12. instrumentation.ts に状態を持たせない

**判断**
データベースとドキュメントストアは初回使用時に解決する。`instrumentation.ts` は起動時の設定チェックだけを行う。

**理由**
当初は `register()` でドライバを注入する設計にした。Next.js のドキュメントは「サーバインスタンス起動時に一度だけ呼ばれ、リクエスト受付前に完了する」と保証しており、注入場所として妥当に見えた。

実際には全リクエストが `No database is configured` で失敗した。**Next.js は instrumentation.ts とルートハンドラが同じモジュールインスタンスを共有することを保証していない。** モジュールレベルのシングルトンは両者の間で共有されない。

**残したもの**
起動時に「サインイン手段が何も設定されていない」場合だけ警告する。これは状態ではなく検査なので、共有されなくても害がない。

## D-13. Worker では password ログインを無効化し、案内を出す

**判断**
Cloudflare Workers 上で Access が未設定の場合、`getLocalAuthDatabase()` は null を返し、`/login` は設定手順を案内する。

**理由**
password 経路は better-sqlite3 を必要とする。Worker はネイティブaddonを読み込めないため、そこへ到達すると例外になる。プレビューで実際に確認したところ、全ページが 500、ログインPOSTも 500、ブラウザには React error #441 だけが出た。**何が悪いのか読み取れない。**

デプロイしたのに Access を設定し忘れる、というのは十分あり得る手順ミスなので、そのときに「何を設定すればよいか」が画面に出る方がよい。

## D-14. 増分キャッシュを構成しない

**判断**
`open-next.config.ts` は `defineCloudflareConfig({})`。R2 増分キャッシュのオーバーライドは使わない。

**理由**
このリーダーは全ルートが認証付きの動的レンダリングで、ビルド出力上の静的ページは `/login` と `/_not-found` だけ。ISRキャッシュに入るものが無い。
`r2IncrementalCache` を設定すると `NEXT_INC_CACHE_R2_BUCKET` という専用バインディングを要求され、プレビューはそれが無いと起動すらしない。使わないキャッシュのためにバインディングを増やす理由がない。

## D-15. Access は Worker 単位で掛ける

**判断**
Cloudflare Access は「ホスト名ごとのアプリケーション」ではなく「Worker を保護する」形で設定する（Workers & Pages → 対象Worker → Access タブ）。

**理由**
Worker 単位の保護は workers.dev ホスト名、カスタムドメイン、ルート、プレビューを**まとめて**対象にする。ホスト名単位だとそのURLしか守られず、`*.workers.dev` を晒したまま独自ドメインだけ保護する、という取りこぼしが起きうる。

副次的に、独自ドメインの割り当てが Access 設定の前提でなくなる。デプロイ → Access 保護 → （必要なら）ドメイン割り当て、の順に進められる。

**手順が古びる前提で書く**
Zero Trust のダッシュボード構成は変わる。この作業中だけで、記憶で書いた手順が3回実物と食い違った。

| 書いていた場所 | 実際（2026-08時点） |
|---|---|
| `Access → Applications` | `Access controls → Applications` |
| `Settings → Authentication`（IdP追加） | `Integrations → Identity providers` |
| （AUD tagの場所を書けていなかった） | アプリの `Configure → Additional settings` |

`docs/HUMAN-TASKS.md` の手順が実物と食い違ったら、記憶で直さず現行ドキュメントを確認すること。

**エージェントが代行できない理由**
`wrangler` の OAuth トークンには Zero Trust / Access のスコープが無い（`wrangler whoami` の scope 一覧で確認済み。workers・d1・pages 等はあるが access は無い）。API トークンを別途発行すれば可能だが、ダッシュボードで数クリックする方が早い。

## D-16. Zero Trust の「team name」「team domain」「ログイン画面の組織名」は別物

**判断**
この3つを混同しない。設定を変えたら、ログイン画面の表示を必ず目視で確認する。

**内訳**

| 名前 | 何か | どこで変えるか |
|---|---|---|
| team domain | `nasu726.cloudflareaccess.com`。JWTの `iss` になる。アプリの設定に入る値 | Zero Trust → Settings |
| team name | 組織の識別名 | Zero Trust → Settings |
| ログイン画面の組織名 | サインイン画面に表示される文字列 | Zero Trust → **Custom pages → Team name and domain → Access login page → Manage** |

**理由**
team domain を変更しても、**ログイン画面の組織名は自動では追随しない**。別の値として保持されている。実際、team domain を `nasu726` に変えた後もサインイン画面には変更前のランダム名が残っていた。

Block page も同じ値を別に持つ。App Launcher は Access login page の値を引き継ぐので個別変更は不要。

**関連する落とし穴**
One-time PIN は **Access ポリシーで許可されたアドレスにしか送信されない**。許可されていないアドレスを入力しても、画面には「コードを送信しました」と表示される。「メールが来ない」の第一容疑者はポリシーの記載漏れであって、メール配送ではない。

## D-17. Access ポリシーはアドレス単位で書く。ドメイン単位は使わない

**判断**
許可は「自分ひとり」に絞る。Worker の Access タブなら `Cloudflare account`、Zero Trust のフルUIなら `Include → Emails`（API上は `email`）にアドレスを列挙する。**ドメインセレクタ（`email_domain`）は使わない。**

**UIによって選択肢が違う**
Worker の Access タブは簡易版で `Cloudflare account` と `Email domain` しか選べない。アドレス単位の `Emails` はフルUI（`Zero Trust → Access controls → Applications → Configure → Policies`）にしかない。個人アカウントなら `Cloudflare account` がメンバー＝自分1人を意味するので、簡易版のままで目的を達成でき、One-time PIN も不要になる。

**理由**
ドメインセレクタは「自組織のドメインに属する全員を許可する」ための機能で、`@example.co.jp` のような**自分が所有するドメイン**を前提にしている。`@gmail.com` を入れると、世界中の Gmail アカウント保持者がこのリーダーに入れる。公開メールプロバイダのアドレスで運用する個人アプリでは、ドメイン単位の許可は「認証を掛けていない」のとほぼ同義になる。

**気づきにくい理由**
Cloudflare は許可されていないアドレスにワンタイムコードを**送らない**が、画面には「コードを送信しました」と表示する。つまり:

- ポリシーが狭すぎる（誰も許可されていない）→「メールが来ない」
- ポリシーが広すぎる（全員許可）→ **何の症状も出ない**

前者はすぐ気づくが、**後者は放置される**。実際、ドメイン欄に完全なメールアドレスを入れていたケースでは前者の症状が出て発覚した。逆だったら気づかなかった。

**運用**
ポリシー変更後は、許可したいアドレスで入れることに加えて、**許可していないアドレスで入れないことを実際に試す**。前者だけの確認では、広すぎる設定を検出できない。

**エージェントには検証できない**
`wrangler` の OAuth トークンに Zero Trust スコープが無いためポリシーを読めず、Access のポリシーが1アドレスしか許可しない以上サインインもできない。この確認は構造的に人間の作業として残る。

## D-18. Access の audience tag はデプロイ外で変わりうる前提で運用する

**判断**
`npm run check:access` を用意し、Access の設定を触った後は必ず実行する。

**理由**
Cloudflare のドキュメントは「AUD tag はアプリケーションを削除・再作成しない限り変わらない」と書いている。実際には、フルUIで作成したポリシーを Worker の Access タブへ適用した直後に値が変わった（`74063d23…` → `86696c70…`）。作り直した意識は無かったので、UI操作が内部でアプリケーションを置き換えたと考えられるが、**確認できていないので断定しない**。

原因より運用上重要なのは、**この不整合が無症状に近い**こと。

- Access は正常に認証する
- アサーションはアプリに届く
- アプリは audience 不一致で黙って拒否する
- 見えるのは「サインインしてもログイン画面に戻る」だけ

ログにも出ない。Access は認証成功として扱い、アプリは仕様通り拒否しているので、どちらも異常を報告しない。

**検出**
`scripts/check-access-config.mts` が、Access のリダイレクトが載せている `kid` と `wrangler.jsonc` の `CF_ACCESS_AUD` を突き合わせる。値を1つ書き換えると赤くなることを確認済み。

**教訓**
一次情報の「変わらない」も、実測が優先する。ドキュメントの保証に依存した設定値は、実際に一致しているか確かめる手段を用意しておく。

## D-19. 無料枠は「行数」ではなく「書き込みリクエスト数」で守る

**判断**
`src/server/usage/write-budget.ts` が、人ごと・UTCの日ごとに**書き込みリクエスト数**を数え、既定2,000を超えたら 429 を返す。認証系（`/api/auth/*`）は対象外。数えられなかった場合は**通す**。

**理由**
D1無料枠は1日10万行の書き込み。支払い方法を登録していないアカウントは課金へ移行せず、**書き込みを拒否し始める**。つまり超過の結果は請求ではなくサービス停止で、原因不明の500がその日いっぱい続く。

行数ではなくリクエスト数を数えるのは、1リクエストが書く行数はたかだか数行である一方、**暴走は必ずリクエスト数として現れる**から。2,000リクエストなら多く見ても1万行未満で、10万行の手前で確実に止まる。読書1日分（400ページのPDFを通読して400回の位置保存、AI1往復につき2行）を大きく上回る。

**なぜ認証系を除外するか**
セーフガードが自分の守っているアプリから締め出せてしまうのは、守っている枠より高くつく。

**なぜ数えられないときに通すか**
逆にすると、マイグレーション適用前にデプロイした瞬間、アプリ内の全保存が静かにエラーになる。守る対象の書き込み自体、DBが本当に壊れていれば独立に失敗する。

**呼び忘れの検出**
`tests/unit/write-budget-coverage.test.mts` が `src/app/api/**/route.ts` を走査し、書き込みメソッドを export する route が `chargeWrite` を呼んでいることを検査する。この保証が崩れる経路は「新しい route を足して呼び忘れる」以外に実質無いため、テストもそこを見る。

## D-20. ハイライトは CSS Custom Highlight API で描く。DOMは書き換えない

**判断**
`src/components/highlight-paint.ts` が `Range` を作って `CSS.highlights` に登録し、`::highlight(book-reader-*)` で着色する。本文に `<mark>` 等を挿入しない。API が無いブラウザでは**何も描かない**。

**理由**
3つの事情が同じ結論を指す。

- pdf.js はページを描き直すたび text layer を作り直すので、挿入した要素は捨てられる
- EPUB本文はサニタイズ済みの著者マークアップで、こちらが要素を足してよいものではない
- 選択・コピー・AIへ渡すテキストが、挿入した要素で変わってはいけない

**位置の求め方が形式ごとに違う理由**
EPUBの `location` には `sectionId` / `startOffset` / `endOffset` が最初から入っているので、**同じ語が章に2回出ても取り違えない**。PDFの `location` はページ番号しか持たないため、text layer から本文を探す。探索時は両辺に同じ正規化（連続空白の圧縮、行末ハイフンとその後の空白の除去）を掛ける。**両者が互いに一致しさえすればよい**ので、`normalizePdfSelectionText` の規則を再現する必要はない。

**副作用として直った欠陥**
選択の境界は常にテキストノードとは限らない。段落をトリプルクリックすると Chrome は要素と子インデックスを返す。テキストノードを走査する `getSectionTextOffset` はそれを見つけられず -1 を返し、**選択そのものが破棄されていた**。その段落はハイライトもAIへの質問もできなかった。

**注意**
Next の CSS 検証は `::highlight` を未知の擬似要素として警告し、そのまま出力する。ビルドログの警告は無視してよいが、将来これが「除去」に変わると**ハイライトは登録され続けたまま何も描かれない**という静かな壊れ方をする。`tests/e2e/highlight-colors.spec.ts` が4つの規則がブラウザに届いていることを検査しているので、その日はテストが落ちる。

## D-21. マニュアルだけ日本語で書く。UIは英語のまま

**判断**
`/help` の本文は日本語。ボタン名だけ英語で引用する（例:「文章を選んで **Highlight** を押す」）。UI本体は英語のまま変えない。

**理由**
読んで理解するための文章に母語を使うことと、UIの言語を変えることは別の問題。マニュアルが必要になった理由は「EPUBというものの存在自体を知らない」「saved highlights が何なのか分からない」で、これは語彙の問題ではなく**説明が無い**問題だった。説明文を第二言語で書けば、解こうとしている問題を薄めるだけになる。

一方でUIの英語は評価済みで、変える理由が無い。ボタン名を訳すと画面と対応が取れなくなるので、引用は英語のままにする。

**認証を通さない理由**
`/help` は server component だが `getCurrentUser()` もDBも参照しない。**サインインが壊れているときにこそ読みたい文書**であり、中身は操作説明だけでユーザーのデータを含まない。本番では Access がホスト全体をエッジで保護しているため、公開範囲は実質変わらない。

## D-22. 右パネルはAIと保存物でタブを分ける

**判断**
`src/components/secondary-tabs.tsx` が右パネルを **AI** と **Saved** に分ける。ハイライト一覧・ノート・単語帳は Saved 側。両方マウントしたまま `hidden` で切り替える。

**理由**
縦に積んでいたので、保存物が**任意の長さの回答の下**にあり、スクロールしないと届かなかった。それ以上に、両者は別の機能である。ハイライトはモデルが一度も関与しなくても残るもので、質問の付随物ではない。

**両方マウントしたままにする理由**
アンマウントすると、書きかけの単語の意味が消え、回答のスクロール位置が先頭へ戻る。タブの切り替えでそれが起きるのは、切り替えを避ける理由になってしまう。

**矢印キー**
`role="tablist"` を名乗る以上、左右キーは動かなければならない。ただしリーダー側の左右キーは window で待ち受けてページを送る。タブバー内の `onKeyDown` で `stopPropagation()` して、タブバーの中では矢印はタブのものにしている。React はルートコンテナでイベントを受けるので、window へ届く前に止まる。

**ついでに直したもの**
ノートのボタンが、一度も書いていない文書で `Clear note` と出ていた。サーバが保持している内容を持つようにして、消すものがあるときだけ `Clear note`、それ以外は `Save note`、どちらでもないときは無効にした。

## D-23. AIパネルは1本の会話にする。モード切り替えをやめる

**判断**
`AiAnswerPanel` を上から下へ読む会話にした。Explain / Translate / Simplify は**モードではなく発言**で、同じ流れに積まれる。入力欄は1つ、送信は `Send` の1つ。

**理由**
以前はモード切り替えだった。Translate を選ぶと Explain の回答が置き換わり、履歴は新しい順に並び、`Ask` というアクションの下に `Follow-up question` という別の入力欄があって同じことをしていた。読書中に「これを説明して、そのうえで訳して、それでこう思ったんだけど」と続けるのは**会話**であって、独立した操作の列ではない。

**会話の主語をアプリ側で保持する**
これが実害の中心だった。アクションの有効・無効を**ブラウザの選択状態**に結び付けていたので、読者がどこかをクリックした瞬間に選択が消え、**全アクションが押せなくなった**。段落を説明させたあと訳させるには、選択し直すしかなかった。いまは会話が「いまの話題（subject）」を保持し、新しい選択が来たときだけ差し替える。

**保存する内容を変えた**
`messages.content` の user 側には**組み立て済みプロンプト**（指示＋文脈＋本文、数百文字）が入っていた。文書を開き直すとそれが全部モデルの発言のように表示され、「askしただけなのにexplainのプロンプトと回答が見える」状態になっていた。いまは `describeUserTurn()` が作る短い1行（`Explain`、`Translate into Japanese`、または質問文そのもの）を保存する。プロバイダへ送るプロンプトはリクエスト内だけに存在する。

副次的に、次のリクエストへ渡す会話履歴も短くなった。以前は履歴として過去のプロンプト全文を積み直していた。

**会話を消せるようにした**
`DELETE /api/ai/action?documentId=`。溜まる一方のものは空にできなければならない（D-19と同じ理由で、D1の1日の書き込み枠にも効く）。

**回答をノートへ**
`Save to notes` が回答を `Document note` へ追記する。会話は流れていくもので、残す価値があるのはその一部だという前提。そのために `DocumentNotes` を `useDocumentNote` フックとビューに分けた。同じノートを2箇所が別々に持つと必ず食い違う。

## D-24. 右パネル自体はスクロールさせない

**判断**
`aside` は `lg:overflow-hidden`。スクロールするのは中身（会話のログ、保存物のタブ）だけ。

**理由**
「微妙な縦スクロール」が発生していた。ペイン全体がスクロールすると、回答が伸びるたびに**下の操作ボタンごと動く**。押す場所が動くのは、読書中の操作としてストレスが大きい。会話ログだけをスクロールさせれば、アクションと入力欄は常に同じ位置にある。

`tests/e2e/ai-answer.spec.ts` が、リーダーは `auto`、ペインは `hidden`、会話ログは `auto` であることを検査する。
